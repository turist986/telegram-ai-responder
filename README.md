# AI Auto-Responder — автоответчик менеджеров в Telegram

Система подменяет менеджера в личных сообщениях Telegram, пока он занят или
недоступен: отвечает через выбранный ИИ-провайдер (по умолчанию DeepSeek,
есть выбор из нескольких — см. «Нейросеть» ниже) на основе базы знаний
компании и настраиваемого промпта, подписывая каждый ответ дисклеймером об
ИИ-происхождении.

Веб-панель адаптивна — открывается и с телефона (боковое меню на узких
экранах сворачивается в гамбургер ☰).

## Архитектура

```
                         ┌─────────────────────────┐
  Клиент ── Telegram ──▶ │  Telethon-клиент (X шт.) │  ← один процесс-воркер,
                         │  по одному на менеджера   │    держит все сессии
                         └────────────┬─────────────┘
                                      │ читает/пишет
                                      ▼
                         ┌─────────────────────────┐
                         │   SQLite (data/app.db)   │  Account, DialogMessage,
                         │                          │  GlobalSetting
                         └────────────┬─────────────┘
                                      │ читает/пишет
                                      ▼
                         ┌─────────────────────────┐
  Админ ── HTTPS ──────▶ │  FastAPI веб-панель       │  Dashboard, Accounts,
     (Nginx/Traefik)     │  (Gunicorn+Uvicorn)      │  Settings, Logs
                         └────────────┬─────────────┘
                                      │
                     ┌────────────────┴────────────────┐
                     ▼                                  ▼
          data/knowledge_base.txt              data/managers.xlsx
          data/prompt_template.txt             (Excel: имя/дисклеймер/статус)
```

Два независимых процесса на одном сервере (два systemd-юнита), обмен
состоянием — через общую SQLite-БД:

- **web** (`app.main:app`, Gunicorn+Uvicorn) — дашборд администратора.
- **worker** (`run_worker.py`) — держит по одному `TelegramClient` (Telethon)
  на каждый включённый аккаунт, слушает входящие личные сообщения, зовёт
  выбранный ИИ-провайдер, отправляет ответ. Каждые
  `RECONCILE_INTERVAL_SECONDS` сверяет список запущенных клиентов с
  тумблерами в БД (вкл/выкл на дашборде, глобальный вкл/выкл, наличие
  .session).

Почему два процесса, а не один: Gunicorn с несколькими воркерами дублировал
бы Telegram-сессии. Поэтому веб-панель запускается с `-w 1`, а вся логика
Telegram/ИИ живёт в отдельном процессе `run_worker.py`.

## Логика дисклеймера

Для каждого сообщения дисклеймер выбирается в порядке приоритета
(`app/services/disclaimer.py`):

1. Столбец **«Дисклеймер»** в `managers.xlsx` для этого аккаунта — если
   заполнен, используется как есть.
2. Иначе — шаблон `DEFAULT_DISCLAIMER_TEMPLATE` из `.env` с подстановкой
   столбца **«Имя менеджера»** (`{name}`).
3. Если и имя не задано — полная заглушка `DEFAULT_FALLBACK_DISCLAIMER`
   (например, «Служба поддержки ООО ТД СК»).

Редактируется всё через `.env` (дефолты) и веб-панель / Excel (данные по
конкретному менеджеру) — без изменения кода.

## Прокси на аккаунт

Если менеджеры и сервер находятся в разных странах, у каждого аккаунта
можно задать свой прокси — это снижает риск того, что Telegram увидит вход
в аккаунт с неожиданно далёкой от менеджера геолокации и заблокирует его
как подозрительный.

Формат: `socks5://user:pass@host:port` (также поддерживаются `socks4://` и
`http://`; логин/пароль необязательны). Указать можно двумя способами —
они равнозначны и не перетирают друг друга при обычной синхронизации:

- **В панели** — раздел «Аккаунты», поле «Прокси» у каждой строки, сохраняется
  сразу по кнопке рядом с полем.
- **В Excel** — столбец «Прокси» в `managers.xlsx`. Учтите: если в
  загружаемом файле такого столбца нет вообще, прокси не трогаются; если
  столбец есть, но ячейка для аккаунта пустая — прокси для него очищается.

Требует пакет `PySocks` (уже в `requirements.txt`). Некорректный формат
прокси панель отклонит сразу при сохранении; если прокси недоступен во
время работы, ошибка появится в столбце «Ошибка» на странице «Аккаунты», а
воркер продолжит пробовать переподключиться на следующей сверке.

## Добавление аккаунта (мастер) и защита от потери аккаунтов

**Прокси обязателен.** Аккаунт без прокси не запускается вообще (`REQUIRE_PROXY=true`
по умолчанию): ни одного соединения с IP сервера. Один прокси — один аккаунт (панель
отклоняет повтор), удалить прокси у аккаунта нельзя — только заменить. Требования к
прокси: статичный (не ротирующийся) IP в стране, откуда менеджер обычно заходит в Telegram.

**«Аккаунты» → «Добавить аккаунт»** (`app/services/onboarding.py`):
1. Ввод идентификатора, номера, прокси. Прокси проверяется на доступ к серверам Telegram.
2. Headless-Chromium (Playwright) заходит на my.telegram.org **через прокси аккаунта**;
   менеджеру в Telegram приходит код, его вводят в панели (в панели виден кадр браузера).
   Сервер создаёт приложение и сохраняет **свой api_id/api_hash для этого аккаунта**.
   Если сайт отказал (CAPTCHA, лимиты) — CAPTCHA не обходится; можно ввести api_id/api_hash вручную.
3. Вход в Telegram (код + 2FA при необходимости) — тем же прокси, тем же api_id и профилем
   устройства, с которыми аккаунт потом работает.
4. Аккаунт создаётся **выключенным**: включите его через 30–60 минут — свежая сессия не
   должна сразу начинать отвечать.

Установка для мастера: `pip install -r requirements.txt` и `playwright install chromium`.

**Профиль устройства** (`services/device_profile.py`): device_model / system_version /
app_version / lang_code выбираются один раз, хранятся в БД и не меняются при рестартах;
разные аккаунты получают разные профили. Свой список: `data/device_profiles.json`.
Мы не выдаём себя за официальный Telegram Desktop — профиль согласован с собственным
приложением аккаунта. Это снижает кластеризацию аккаунтов, но не делает их «невидимыми»:
MTProto-отпечаток Telethon полностью скрыть нельзя.

**Импорт из TData** («Аккаунты» → «Импорт TData» → `/accounts/import-tdata»; включён по
умолчанию, выключается `ALLOW_TDATA_IMPORT=false`). Как пользоваться (массово):
1. Перетащите на страницу один или несколько архивов **.zip / .rar** — в каждом может лежать
   одна или много папок `tdata` (формат определяется по содержимому, а не по расширению).
   Кеш профиля Desktop (`user_data`, эмодзи, словари) при распаковке пропускается, поэтому
   большие архивы допустимы; небезопасные пути в архиве (`..`, абсолютные) отклоняются.
2. Впишите прокси — **по строке на аккаунт, в порядке аккаунтов** (порядок по названиям папок:
   1, 2, 10…). Идентификаторы берутся из названий папок (`1\tdata` → `1`) или из имени архива,
   если `tdata` лежит в корне; можно задать свои.
3. При необходимости укажите пароль архива, локальный код Telegram Desktop и облачный пароль
   (2FA) — они применяются ко всем аккаунтам загрузки и нигде не сохраняются.
4. Нажмите «Импортировать»: всё проверяется **до первого обращения к Telegram** (нет прокси /
   дубль прокси / повторяющиеся идентификаторы — не импортируется ничего), затем аккаунты
   входят по одному с паузами, а на странице виден ход выполнения; ошибка одного аккаунта
   (например, «сеанс в этой TData недействителен») не отменяет остальные. Аккаунты, у которых
   уже есть сессия, пропускаются (или перезаписываются, если отметить «Заменить»).
5. `.rar`: сжатые архивы распаковывает внешняя программа — 7-Zip (`winget install 7zip.7zip`),
   UnRAR или bsdtar (в Windows 10+ встроенный `tar.exe` подхватывается сам); без неё панель
   подскажет, что поставить, либо запакуйте в `.zip`. Формат `.7z` не поддерживается.

Ключевое устройство импорта:
- TData конвертируется через opentele `CreateNewSession`, а не `UseCurrentSession`: создаётся
  **новый, отдельный сеанс со своим auth_key**, который виден в Telegram как самостоятельное
  устройство и **не делит ключ с Telegram Desktop**. `UseCurrentSession` буквально копирует
  ключ живого Desktop — тогда воркер (через прокси) и сам Desktop (напрямую/через VPN)
  работают под одной записью сеанса, и Telegram видит «одно устройство, которое прыгает
  между IP» (плюс риск `AUTH_KEY_DUPLICATED`).
- `CreateNewSession` делает реальные подключения к Telegram, поэтому они идут **только через
  прокси аккаунта** (без прокси импорт отклоняется), иначе реальный IP машины с панелью
  попал бы в Telegram при самом импорте.
- Один аккаунт можно загрузить и через форму на странице «Аккаунты» (идентификатор + прокси +
  zip с папкой `tdata`); пакетная загрузка через Excel + один zip тоже работает.
- Импортированные аккаунты создаются выключенными (остывание новой сессии); TData перед
  импортом лучше брать с закрытым Telegram Desktop — ключ одновременно открытого Desktop и
  нашего одноразового подключения может быть аннулирован Telegram (`AUTH_KEY_DUPLICATED`).
- Импорт готовых `.session`-файлов (`ALLOW_LEGACY_SESSION_IMPORT`, включён по умолчанию) работает
  как раньше: такие сессии рождены с чужим api_id/IP.
Аккаунты без собственного api_id или профиля помечены в таблице и продолжают работать на
общем api_id из `.env` (назначить свой — «общий api_id (назначить)» в таблице).

**Настройки → «Защита аккаунтов»** (применяются без перезапуска воркера):
- *Период проверки обновлений* — пресеты «Стандарт / Реалистичный (высокий разброс) / Тихий»
  или свои значения (период, разброс %, период проверки непрочитанных).
- *Темп ответов* — «сессия»: первые N ответов быстрые, затем задержка плавно растёт
  (менеджер «взял телефон»); характер сессии (быстрее/медленнее) случайный и держится до
  конца сессии; либо фиксированный диапазон. «Печатает…» показывается по длине ответа.
- *Автостоп при FloodWait/PeerFlood* — аккаунт целиком замолкает на паузу
  `(требование Telegram + запас) × множитель^(серия−1)`, не короче требования Telegram и не
  длиннее потолка; серия сбрасывается через заданное время без флудов. Пауза хранится в БД
  (переживает рестарт), сообщения клиентов в это время попадают в «Логи». Telethon
  настроен с `flood_sleep_threshold=0`, поэтому FloodWait не «пережидается» молча.
- *Возрастной порог ответа* — не отвечать на сообщения старше N минут (можно выключить).

Тесты: `python -m unittest discover -s tests -t .` (работают на временной БД, к Telegram не подключаются).

## Расписание работы

Раздел «Настройки» → «Расписание работы» — три независимых переключателя,
действуют глобально на все аккаунты (`app/services/schedule.py`):

1. **Ограничивать по рабочим часам** — ИИ отвечает только в заданных
   периодах. Периодов может быть несколько (кнопка «Добавить период
   работы») — например, сплит-график `09:00–13:00` и `15:00–20:00`; можно
   задать и ночное окно вроде `22:00–06:00`, через полночь. Вне всех
   периодов входящее сообщение по-прежнему логируется (видно на странице
   «Логи»), но ответ не отправляется.
2. **Учитывать перерыв (обед)** — тоже список из одного или нескольких
   окон (кнопка «Добавить период перерыва»), например обед + короткий
   перерыв на кофе, действуют *внутри* рабочих часов — в это время ИИ
   тоже не отвечает.
3. **Не обрывать уже начатый диалог с клиентом вне расписания** — если
   включено, для клиента, которому ИИ уже отвечал позже переданного в
   «Таймаут бездействия клиента» количества минут назад, ответы
   продолжаются даже вне расписания. Как только клиент молчит дольше
   таймаута, ограничение по расписанию снова вступает в силу. Без этой
   опции диалог просто обрывается ровно в момент конца рабочего дня/начала
   перерыва.

Время читается из локального времени сервера — часовой пояс сервера должен
совпадать с часовым поясом бизнеса (или его нужно явно выставить в ОС/Docker).
Некорректно сохранённое расписание (не должно происходить при сохранении
через панель — она валидирует формат) не блокирует ответы: воркер логирует
проблему и работает так, будто ограничение по времени выключено.

## Нейросеть (выбор ИИ-провайдера)

Раздел «Настройки» → «Нейросеть» позволяет выбрать, какой ИИ генерирует
ответы, без изменения кода. Поддерживаются (`app/services/llm_providers.py`):

| Провайдер | Переменная в `.env` | Модель по умолчанию |
|---|---|---|
| **DeepSeek** (по умолчанию) | `DEEPSEEK_API_KEY` | `deepseek-chat` |
| OpenAI | `OPENAI_API_KEY` | `gpt-4o-mini` |
| Anthropic Claude | `ANTHROPIC_API_KEY` | `claude-3-5-haiku-20241022` |
| Groq | `GROQ_API_KEY` | `llama-3.3-70b-versatile` |
| Mistral | `MISTRAL_API_KEY` | `mistral-large-latest` |
| OpenRouter (доступ к десяткам моделей) | `OPENROUTER_API_KEY` | `deepseek/deepseek-chat` |

Ключ можно вставить прямо в панели («Настройки» → «Нейросеть» → «Ключи
API» — поле для каждого провайдера, значение маскируется и повторно на
экран не выводится) или задать через `.env`. Если задано и там, и там —
приоритет у значения из панели. Кнопка с корзиной удаляет ключ, сохранённый
в панели (после этого снова используется `.env`, если он там есть). Если
для выбранного провайдера не задан ключ ни одним из способов, попытка
ответа завершится ошибкой, которая появится в столбце «Ошибка» на странице
«Аккаунты» — сам сервис не упадёт.

Все перечисленные провайдеры, кроме Anthropic, используют один и тот же
OpenAI-совместимый формат `/chat/completions`, поэтому добавить ещё одного
(например, свой self-hosted эндпоинт) — это одна запись в
`llm_providers.py` без изменения остального кода.

## Установка (локально / на сервере)

```bash
cd telegram-ai-responder
python -m venv venv
venv\Scripts\activate        # Windows
# source venv/bin/activate   # Linux/macOS
pip install -r requirements.txt

copy .env.example .env       # Windows; на Linux: cp .env.example .env
```

Заполните `.env`:
- `TELEGRAM_API_ID` / `TELEGRAM_API_HASH` — https://my.telegram.org
- `DEEPSEEK_API_KEY` — https://platform.deepseek.com (или ключ другого
  провайдера из таблицы в разделе «Нейросеть» выше — какой выбрать,
  настраивается потом в панели)
- `SECRET_KEY` — `python -c "import secrets;print(secrets.token_hex(32))"`
- `ADMIN_PASSWORD_HASH` — `python scripts/hash_password.py`

Создайте пример таблицы менеджеров (или сразу загрузите свою через панель):

```bash
python scripts/create_managers_template.py
```

Отредактируйте `data/knowledge_base.txt` и `data/prompt_template.txt` под
вашу компанию (или сделайте это позже через раздел «Настройки»).

### Получение .session для каждого менеджера

Сервер не может интерактивно запросить код подтверждения, поэтому сессию
нужно один раз авторизовать локально:

```bash
python scripts/create_session.py 79991234567
```

Скрипт запросит номер телефона и код из Telegram, создаст
`data/sessions/79991234567.session`. Этот файл либо скопируйте прямо в
`data/sessions/` на сервере, либо загрузите через панель («Аккаунты» →
«Загрузить .session»). `79991234567` должен совпадать со значением в
столбце «Аккаунт» в `managers.xlsx`.

Импорт из TData (папка профиля Telegram Desktop) — через панель, см. раздел
«Импорт из TData» выше; он требует дополнительно (`start_local.bat` делает это сам):
```bash
python scripts/install_tdata_deps.py
```
Почему отдельным скриптом, а не `pip install -r`: opentele тянет `tgcrypto`, который собирается
из исходников и требует компилятор C++ (Microsoft C++ Build Tools / `build-essential`) — на
чистом сервере обычная установка падает, и импорт TData оказывается недоступен. Скрипт ставит
opentele без `tgcrypto` (`--no-deps`), PyQt5 отдельно, а вместо `tgcrypto` проект использует
чистый Python-шим (`app/services/_opentele_compat.py`). Если TData не нужен — скрипт можно не
запускать; в панели, если пакета нет, импорт покажет подсказку с этой командой.

**Обновление сервера одной командой.** В папке проекта (на Windows VPS — в PowerShell или cmd
«от имени администратора», иначе задачи Планировщика не перезапустить):

```bash
.\update.bat
```
(в cmd — просто `update.bat`; на Linux — `bash deploy/update.sh`). Скрипт делает всё сам:
`git pull` → доустанавливает зависимости (`requirements.txt`, при необходимости пакеты для TData) →
перезапускает сайт и воркера (задачи `AIResponderWeb`/`AIResponderWorker`, а если изменился
`deploy\Caddyfile` — и `AIResponderCaddy`) → ждёт, пока панель ответит, и пишет «Готово» (или
показывает конец лога). Если обновлять нечего — так и скажет и ничего не перезапустит
(`update.bat -Force` — переустановить и перезапустить всё равно; `-NoRestart` — только код и
зависимости).

- Свои правки отслеживаемых файлов (например, домен в `deploy\Caddyfile`) не мешают: скрипт
  использует `git pull --autostash`. `.env`, `data\` (база, сессии) и `venv` вне git и не
  затрагиваются.
- Если сайт запущен через `start_local.bat`, а не как задачи, скрипт обновит код и зависимости и
  напомнит перезапустить окна вручную.
- **Один раз** после появления этого скрипта на сервере: `git pull --autostash`, дальше —
  только `.\update.bat`.

Вручную то же самое: `git pull`, `venv\Scripts\python.exe -m pip install -r requirements.txt`,
`venv\Scripts\python.exe scripts\install_tdata_deps.py`,
`Stop-ScheduledTask` и `Start-ScheduledTask -TaskName AIResponderWeb,AIResponderWorker`.
Код Python подхватывается только после перезапуска; шаблоны и статика — сразу.
(`start_local.bat` сверяет зависимости при каждом запуске сам.)

**Лимит загрузки:** в `deploy/Caddyfile` и `deploy/nginx.conf` стоит 1 ГБ (архивы профилей
Desktop бывают большими). Если панель стоит за другим прокси/CDN (например, Cloudflare на
бесплатном тарифе режет тела запросов больше 100 МБ) — упаковывайте только нужное: папку
`tdata` без `user_data`/`emoji`.

### Локальный запуск (Windows, в один клик)

Проще всего — двойной клик по `start_local.bat` в папке проекта. Скрипт сам
создаст виртуальное окружение, поставит зависимости и поднимет весь сайт:
и веб-панель, и воркера (ответы в Telegram) — каждый в своём окне (по
названию «AI Responder - site» / «AI Responder - worker»), плюс откроет
браузер на `http://localhost:8000`. При первом запуске (если нет `.env`)
откроет его в блокноте — впишите туда реальные значения и запустите
`start_local.bat` ещё раз. Не закрывайте открывшиеся окна, пока пользуетесь
системой; если что-то упадёт при старте — окно останется открытым с текстом
ошибки, а не закроется само. Только панель без воркера — вручную:
`venv\Scripts\python.exe -m uvicorn app.main:app --port 8000`.

**Важно:** открывать файлы из `app/templates/*.html` напрямую в браузере
(двойным кликом, через «Открыть файл») — не сработает и не должно: это
серверные шаблоны Jinja2 (со синтаксисом `{% ... %}`), они превращаются в
обычный HTML только когда их отдаёт запущенный сервер. Всегда заходите
через адрес `http://localhost:8000` (или ваш домен), а не через путь к
файлу на диске (`C:\...` в адресной строке — верный признак этой ошибки).

### Локальный запуск (вручную)

```bash
# терминал 1 — веб-панель
uvicorn app.main:app --reload --port 8000

# терминал 2 — воркер Telegram
python run_worker.py
```

Откройте http://localhost:8000, войдите под `ADMIN_USERNAME` / паролем,
который хэшировали выше.

## Деплой на продуктовый сервер (Linux + домен + HTTPS)

1. Скопируйте проект в `/opt/ai-responder`, создайте venv, установите
   зависимости, заполните `.env` как выше.
2. Создайте системного пользователя `ai-responder` и выдайте ему права на
   `/opt/ai-responder`.
3. Установите systemd-юниты и включите оба сервиса:

```bash
sudo cp deploy/systemd/ai-responder-web.service /etc/systemd/system/
sudo cp deploy/systemd/ai-responder-worker.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now ai-responder-web ai-responder-worker
sudo systemctl status ai-responder-web ai-responder-worker
```

4. Настройте Nginx (домен + SSL через certbot):

```bash
sudo cp deploy/nginx.conf /etc/nginx/sites-available/ai-responder.conf
# отредактируйте server_name на ваш домен
sudo ln -s /etc/nginx/sites-available/ai-responder.conf /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx

sudo certbot --nginx -d your-domain.example
```

После этого панель доступна по `https://your-domain.example`. Конфиг Nginx
уже проксирует `Upgrade`/`Connection` заголовки — если позже добавите
live-обновление логов через WebSocket, менять Nginx не потребуется.

Для Traefik: эквивалент — роутер на `Host(\`your-domain.example\`)` с
`tls.certresolver` на ваш ACME-резолвер и `loadbalancer.server.port=8000`,
проброс на тот же 127.0.0.1:8000 (или сервис в докер-сети).

## Деплой на VPS под Windows (Caddy)

Альтернатива разделу выше — для тех, у кого сервер на Windows, а не Linux.
Caddy выбран вместо Nginx намеренно: он сам получает и продлевает
HTTPS-сертификат (Let's Encrypt) без `certbot` и ручной возни с cron —
достаточно указать домен в `Caddyfile`. `gunicorn` (из systemd-юнита выше) на
Windows не работает (полагается на `fork()`), поэтому здесь везде — обычный
`uvicorn`, что и так соответствует требованию «один воркер веб-процесса» из-за
блокировки сессий Telethon.

1. Установите Python 3.11+ и склонируйте проект, например в `C:\ai-responder`:
```bash
git clone https://github.com/<ваш-репозиторий>/telegram-ai-responder.git C:\ai-responder
cd C:\ai-responder
python -m venv venv
venv\Scripts\pip install -r requirements.txt
copy .env.example .env
REM заполните .env — см. раздел "Установка" выше
```

2. Установите Caddy (открыть новое окно PowerShell после установки, чтобы обновился PATH):
```bash
winget install CaddyServer.Caddy
```

3. Отредактируйте `deploy\Caddyfile` — впишите свой домен вместо
   `your-domain.example` и реальный путь к проекту вместо `C:\ai-responder`
   (домен должен указывать A-записью на этот сервер).

4. Зарегистрируйте веб-панель, воркера и Caddy как фоновые задачи Windows
   (автозапуск при старте системы, автоперезапуск при сбое) — **от имени
   администратора**:
```bash
cd C:\ai-responder
.\deploy\windows\install-services.ps1
```
   Скрипт использует только штатный Планировщик заданий Windows — никаких
   сторонних инструментов (NSSM и т.п.) ставить не нужно. Он же один раз
   открывает порты 80/443 в брандмауэре Windows.

5. Проверка:
```bash
Get-ScheduledTask -TaskName AIResponderWeb,AIResponderWorker,AIResponderCaddy | Get-ScheduledTaskInfo
```
   Логи — `data\service-web.log`, `data\service-worker.log`,
   `data\service-caddy.log`. Панель — на `https://ваш-домен` (сертификат
   Caddy выпустит сам при первом запросе, обычно занимает несколько секунд).

   Остановить всё: `Stop-ScheduledTask -TaskName AIResponderWeb,AIResponderWorker,AIResponderCaddy`.
   Удалить всё: `Unregister-ScheduledTask -TaskName AIResponderWeb,AIResponderWorker,AIResponderCaddy -Confirm:$false`.

## Важные оговорки

- **ToS Telegram.** Автоматизация *личных* (не бот-) аккаунтов через
  Telethon технически образует «userbot»-сценарий. Массовая или спамная
  автоматизация запрещена правилами Telegram и может привести к
  ограничению аккаунта; точечные автоответы реальным входящим клиентам —
  распространённая практика среди CRM-интеграций, но риск ограничения
  аккаунта при агрессивном использовании (многие сообщения в минуту,
  массовые рассылки) остаётся на стороне владельца аккаунта. Держите
  задержки перед ответом (`TYPING_DELAY_MIN/MAX`) реалистичными и не
  используйте систему для исходящих холодных рассылок.
- **Масштаб.** SQLite + polling каждые `RECONCILE_INTERVAL_SECONDS` хорошо
  работает для десятков аккаунтов. Для сотен менеджеров стоит перейти на
  PostgreSQL и заменить polling на Redis pub/sub между веб- и
  worker-процессом.
- **Бэкапы.** `.session` файлы — это полный доступ к личному аккаунту
  Telegram менеджера. Храните `data/sessions/` и `.env` так же, как пароли
  (права доступа, не в общедоступном git-репозитории).
